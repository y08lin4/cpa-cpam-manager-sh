# CPA Manager Plus 运维脚本功能整合与优化规划

## 1. 文档目的

本文不是单纯罗列“还能增加什么功能”，而是对当前 `cpa-cpam-manager.sh` 做一次完整的产品治理盘点，明确：

- 哪些功能继续保留并加强。
- 哪些功能应该合并，减少重复入口和重复确认。
- 哪些功能应该拆开，避免风险边界混乱。
- 哪些旧入口、旧叫法和兼容逻辑应该删除。
- 哪些新功能值得优先开发。
- 最终一级菜单应该如何排序。
- 每个阶段如何实施、兼容和验收。

规划对象包括三个项目边界：

1. 本仓库的安装运维脚本。
2. CLIProxyAPI 提供的代理、凭证、模型和 Management API 能力。
3. CPA Manager Plus 提供的用量、配置和可视化管理能力。

本文遵守已确认的交互原则：**主要功能全部直接显示在一级菜单，不建立“部署管理 → 再选择操作”之类的多级功能目录。** 菜单中的“部署管理、运行维护、数据与迁移、审计与安全”仅作为视觉分区标题，不需要进入。

## 4. 建议合并的功能

### 4.1 已执行：合并“迁移预检”和“查看迁移计划”

#### 当前问题

当前两个入口是：

```text
11) 迁移预检
12) 查看迁移计划
```

“查看迁移计划”本身会先运行迁移预检，因此两个入口会重复读取容器、挂载、版本和配置。对普通用户来说，也很难理解为什么查看计划前还要单独跑一次预检。

#### 建议方案

已经合并为一个一级入口：

```text
迁移评估（只读）
```

一次性展示：

1. 当前安装类型：`legacy`、`plus`、`mixed` 或未安装。
2. 当前容器、镜像和运行状态。
3. `/data` 实际挂载来源。
4. SQLite、`data.key`、Compose 和密钥文件是否齐全。
5. 是否允许自动迁移。
6. 预计停机范围。
7. 迁移步骤。
8. 自动回滚条件。
9. 迁移前需要用户处理的问题。

#### 保留边界

- “正式迁移到 Plus”继续保持独立入口。
- “回滚最近迁移”继续保持独立入口。
- 迁移评估不修改文件、不停止容器、不拉取镜像。

#### 命令兼容

- 新命令为 `migration-assess`。
- `preflight` 和 `migrate --dry-run` 当前只输出弃用提示并调用同一评估逻辑。
- 下一次大版本删除重复的旧命令解析分支。

### 4.2 合并重复的状态采集底层逻辑，不合并菜单入口

“状态 / 健康检查”“升级检查”“迁移评估”“安装完成验收”和“诊断包”都会读取相同信息：

- 安装目录。
- 容器与镜像。
- 端口映射。
- 健康端点。
- 密钥文件是否存在。
- 数据目录和磁盘状态。

建议底层统一成一个只读状态采集器，同时支持：

```text
终端可读输出
JSON 输出
Markdown 诊断摘要
```

这是代码层合并，不是菜单层合并。用户仍然直接选择状态、升级或迁移，不进入多级页面。

### 4.3 合并公网 IP 查询的公共逻辑

消费行为审计和管理行为审计都需要：

- IP 排名。
- 内网、公网、回环分类。
- IP-API Batch 查询。
- 归属结果格式化。

这部分应继续共用一套底层函数，但两个审计的输入、统计和页面必须完全独立。不能因为复用代码再次把消费与管理数据合并。

### 4.4 合并快照元数据和系统保护点格式

人工快照、安装初始快照、升级前保护点、密钥重置前保护点、恢复前保护点和迁移快照应逐步使用统一元数据字段：

```text
快照 ID
类型
创建原因
创建时间
备注
归档大小
SHA-256
CPA 镜像及摘要
Plus 镜像及摘要
脚本版本
包含内容
恢复兼容范围
```

目录仍按 `manual`、`system`、`migration` 分开；合并的是格式和校验逻辑，不是把文件重新堆到同一个目录。

## 5. 建议拆分的功能

### 5.1 拆分“查看密钥 / 地址”

#### 当前问题

访问地址属于低敏感运维信息，API Key、CPA Management Key 和 Plus 管理员密钥属于高敏感凭证。把两者放在同一个入口会导致用户只想复制地址时，终端却显示完整密钥，增加截图、录屏和命令历史泄露风险。

#### 建议拆分

```text
查看访问地址
查看敏感密钥
```

“查看访问地址”直接显示：

- CPA API 地址。
- CLIProxyAPI 管理页面。
- CPA Manager Plus 页面。
- 端口和当前可访问状态。

“查看敏感密钥”默认只显示：

```text
API_KEY=sk-cpa-****c82f
MGT_KEY=mgt-cpa-****91ad
CPAMP_ADMIN_KEY=cpamp_****7e32
```

只有再次明确确认后才显示完整值，并提示不要截图、不要粘贴到 Issue。

### 5.2 不拆分“重新生成管理密钥”的三个范围到一级菜单

密钥重置内部目前可以选择：

1. 只重置 Plus 管理员密钥。
2. 只重置 CPA Management Key。
3. 两个全部重置。

虽然项目要求主要功能一级直达，但这里三个选项属于同一个高风险事务的作用范围，而不是三个独立日常功能。如果全部提升到一级菜单，会让危险操作占据多个位置，也更容易误选。

建议保留一个“重新生成管理密钥”一级入口，进入后只选择作用范围；确认页必须再次显示将重置哪一个密钥、会停止哪些服务、保护快照位置和失败回滚方式。

### 5.3 不合并也不拆分两套行为审计

以下两个入口必须保持独立：

```text
消费行为审计
管理行为审计
```

每套内部再展示成功和失败，这是统计维度，不应继续拆成四个一级菜单。这样既满足消费与管理分离，也避免菜单出现“消费成功、消费失败、管理成功、管理失败”四个高度相似入口。

### 5.4 不合并快照创建、查看和恢复

三项操作的风险不同：

- 创建快照：新增文件，低风险。
- 查看快照：只读，低风险。
- 恢复快照：覆盖配置和数据，高风险。

必须继续保持三个一级入口。尤其不能做一个“快照管理”入口后再进入二级菜单，因为这与已经确认的一级直达要求冲突。

## 6. 建议删除或退役的功能

### 6.1 删除旧混合行为入口

旧菜单“安全巡检 / 24h IP”已经被消费行为审计和管理行为审计替代，不应恢复。

`security` 兼容命令已经删除。README 和菜单只展示 `audit-consumption` 与 `audit-management`。

### 6.2 删除旧备份命令和旧目录叫法

`backup` 已被可查看、可备注、可恢复的快照功能替代。后续不建议恢复：

- `backup` 菜单或命令。
- `backups/` 作为新的默认目录。
- “常规备份文件”与“迁移快照”混放。

如果检测到历史 `backups/`，只应提示“发现旧格式归档”，允许用户查看路径或手工导入，不应静默删除。

### 6.3 删除独立的“查看迁移计划”入口

在“迁移评估”完成后，独立计划入口没有继续保留的价值。删除的是重复菜单入口，不删除计划内容。

### 6.4 删除不带路径的模糊日志推断

行为审计不能把诸如：

```text
request from 203.0.113.10 status=500
unauthorized from 198.51.100.8
```

这种没有明确 HTTP 方法和路径的普通日志猜成消费或管理行为。它们最多进入诊断计数，不能污染任何排行榜。

### 6.5 删除自动封禁 IP 的默认设想

现阶段不加入“一键自动封禁排行榜 IP”。公网 NAT、公司出口、代理、Cloudflare 和家庭宽带都可能造成误伤。

可以保留“生成防火墙建议”作为未来功能，但必须包含证据、规则有效期和撤销命令，默认不执行。

### 6.6 不删除用户原始数据和上游日志

以下任何“清理”功能都不得删除：

- CLIProxyAPI 原始日志。
- CPA Manager Plus SQLite。
- OAuth 和认证文件。
- `data.key`。
- Compose 和密钥配置。
- 上游程序自己的统计记录。

“清除审计记录”只能推进本脚本独立的显示基线。

## 7. 建议优先新增的功能

### 7.1 P0：清除审计显示记录

用户可以选择：

1. 只清除消费行为审计显示记录。
2. 只清除管理行为审计显示记录。
3. 两套都从当前时间重新开始显示。

实现方式是写入独立的 `.audit-state.json`，不执行 `rm`、`truncate`，不修改 SQLite。确认页必须显示旧基线、新基线和“源日志不会删除”。

### 7.2 P0：查看全部审计历史

临时忽略显示基线，读取现有日志中仍然存在的全部历史。该操作只读，不修改清除状态。

如果历史日志已经被 Docker 或上游轮转删除，必须显示“源日志已不存在”，不能假装可以恢复。

### 7.3 已实现：配置体检

新增 `doctor` 命令和一级菜单入口，检查：

- Compose 是否能解析。
- `config.yaml` 语法及关键字段。
- 端口是否冲突。
- 容器名称是否冲突。
- bind mount 是否指向预期路径。
- `.secrets.txt`、`data.key` 权限。
- SQLite `quick_check`。
- 镜像与运行容器是否漂移。
- 磁盘剩余空间是否足以快照和升级。
- 是否存在新旧 Manager 同时运行。

配置体检默认只读，不自动修复。

### 7.4 P0：快照恢复演练

现有恢复会实际覆盖生产数据。新增只读恢复演练：

1. 校验元数据和 SHA-256。
2. 解压到临时隔离目录。
3. 检查 Compose、密钥、`data.key` 和 SQLite。
4. 执行 SQLite `quick_check`。
5. 判断当前脚本和镜像是否能识别该快照。
6. 输出可恢复、警告或不可恢复结论。

默认不启动第二个 Manager，避免两个 Manager 同时消费用量队列。

### 7.5 P0：脱敏诊断包

遇到故障时生成本地 Markdown 或压缩包，包含：

- 脚本版本。
- 操作系统和 Docker 版本。
- 容器状态、镜像摘要和端口。
- 健康检查结果。
- 脱敏后的 Compose 和配置结构。
- 最近日志中的错误摘要。
- 快照清单和磁盘空间。
- 用户执行过的动作时间线。

生成前和生成后都要扫描密钥、Token、Authorization 和凭证正文。脚本只生成本地文件，不自动上传。

### 7.6 已实现：删除指定快照

现有快照只增不减，长期会占满磁盘。新增删除指定快照功能，但必须满足：

- 只允许删除 `snapshots/manual` 和 `snapshots/system` 下带合法元数据的受管目录。
- 拒绝符号链接和越界路径。
- 展示编号、时间、类型、大小、备注和 SHA-256。
- 默认不允许删除最新系统保护点。
- 删除前输入快照编号并再次确认。
- 不提供“清空全部快照”快捷操作。

### 7.7 已实现基础版：定时快照与滚动保留

当前支持每天或每周通过 systemd timer 创建快速不停机快照，并配置保留最近 1-100 个 `scheduled-*`。滚动清理不会触碰人工快照和其他系统保护点。后续可继续扩展按天数保留。

当前策略：

```text
人工快照：永久保留，手工删除
系统保护点：保留最近 10 个或 30 天
迁移快照：默认永久保留
```

首次启用前会展示频率、保留数量和不会自动删除的范围。保留策略不能删除初始安装、升级前、密钥重置前、恢复前或迁移快照。

### 7.8 P1：凭证健康检查

只读取认证文件元数据和可安全解析字段：

- 文件数量和供应商分类。
- 空文件、损坏 JSON、权限异常。
- 明确的过期时间。
- 最近更新时间。
- 连续 401、403 或刷新失败。
- 被禁用或冷却中的账号。

不得输出 OAuth Token、Refresh Token、Cookie 或完整账户标识。

### 7.9 P1：磁盘与容量检查

统一展示：

- 根分区剩余空间。
- `logs/`、`snapshots/`、`cpa-manager-data/` 大小。
- 最近 7 天增长速度。
- 按当前速度预计占满时间。
- 可以安全处理的项目建议。

默认只给建议，不自动删除日志、快照或数据库。

### 7.10 P1：升级观察窗口

升级完成后持续观察一段时间：

- 两个容器是否持续运行。
- `/health`、`/status`、`/v1/models` 是否稳定。
- 是否出现连续 5xx、401 或 403。
- 容器是否重启或 OOM。

达到失败阈值时提示使用升级前系统快照回退。默认不发起会产生模型费用的真实消费请求。

### 7.11 P1：统一 JSON 输出

为状态、审计、快照列表、迁移评估和配置体检提供 `--json`，方便监控或自动化调用。必须定义版本字段和稳定退出码，不能把彩色终端文本直接当作接口。

### 7.12 P2：计划任务中心

生成并管理 systemd timer，用于：

- 定时创建快照。
- 定时配置体检。
- 版本检查。
- 凭证到期检查。
- 磁盘容量检查。
- 审计摘要报告。

任务默认生成但不启用；启用前展示时间、频率、磁盘影响和锁冲突策略。

## 8. 建议暂缓的功能

### 8.1 多实例管理

多实例需要重新设计容器名、Compose 项目、安装目录、端口、状态文件、快照库和菜单当前上下文。当前单实例的恢复与审计闭环没有完全完成前，不建议提前引入。

### 8.2 多服务器批量升级

批量只读巡检可以先做，但批量升级会放大同一版本故障。应先完成固定镜像摘要、恢复演练和观察窗口，再讨论分批升级。

### 8.3 动态模型路由和熔断

这属于 CLIProxyAPI 上游能力。外部 Bash 脚本不能可靠复制其真实路由决策，应该通过上游稳定接口实现。

### 8.4 团队预算、配额和计费

需要上游提供结构化调用主体、准确价格表和并发一致性控制。仅靠日志推断不能用于强制停用或正式账单。

### 8.5 完整 Web 运维控制台

本仓库不应重新实现一个与 CPA Manager Plus 重复的后台。脚本适合部署、恢复和宿主机运维；业务用量与交互界面应优先在 Plus 中完善。

### 9.2 为什么不追求更少的菜单项

这个项目包含安装、凭证、快照、迁移和卸载等高风险能力。过度合并会产生两个问题：

1. 用户必须进入二级菜单才能知道有哪些能力，违背一级直达要求。
2. 只读操作和覆盖数据的写操作混在同一入口，容易误操作。

因此只合并真正重复的迁移预检与计划，其他风险边界不同的功能宁可直接显示。

### 9.3 编号调整策略

菜单编号应该按功能区域连续排列，不能继续按开发先后把新功能插到 `17`、`18`、`20`。

为了避免熟悉旧编号的用户误操作：

- 第一个版本同时展示“功能名称”，确认页不能只显示编号。
- 所有危险操作在确认页重新显示功能名称、目标和影响。
- 命令行名称保持稳定，不受菜单编号调整影响。
- README 截图和测试必须同步更新。

## 12. 实施阶段

### 阶段 A：菜单与风险边界治理

实施内容：

1. 合并迁移预检和计划为迁移评估。
2. 拆分查看地址与查看密钥。
3. 连续重排一级菜单编号。
4. 给旧命令增加明确弃用提示。
5. 为菜单内容增加自动测试。

完成标准：

- 所有主要能力一级直达。
- 编号连续、功能分区清楚。
- 只读与高风险写操作不混在同一个入口。
- 旧编号变化不会绕过危险确认。

### 阶段 B：可靠性闭环

实施内容：

1. 配置体检。
2. 快照恢复演练。
3. 脱敏诊断包。
4. 清除审计显示记录。
5. 查看全部审计历史。

完成标准：

- 配置变更前可以发现明显错误。
- 快照能证明可恢复，不只证明能解压。
- 审计清除不修改任何上游数据。
- 故障材料可以安全交给维护者排查。

### 阶段 C：主动运维

实施内容：

1. 凭证健康检查。
2. 磁盘与容量检查。
3. 删除指定快照。
4. 快照保留策略。
5. 升级观察窗口。
6. 统一 JSON 输出。

完成标准：

- 常见容量、凭证和升级风险能在故障前发现。
- 自动化读取稳定结构，不解析彩色终端文本。
- 删除动作有明确对象、证据和回退边界。

### 阶段 D：规模化能力

实施内容：

1. 计划任务中心。
2. 异地加密快照副本。
3. 多实例档案。
4. 多主机只读巡检。
5. 通用告警适配器。

开始条件：阶段 A 至 C 已稳定，快照恢复和状态输出有自动回归测试。

## 13. 统一交互规范

每个写操作确认页必须显示：

- 当前功能名称。
- 安装目录和目标实例。
- 当前容器状态。
- 将修改或删除的对象。
- 是否停机及预计范围。
- 保护快照位置。
- 失败后的自动回退方式。
- 默认确认值。

每个列表页必须：

- 使用固定列宽或分块卡片。
- 正常显示绿色 `✓`。
- 警告显示黄色 `!`。
- 失败显示红色 `✗`。
- 无数据与查询失败使用不同文案。
- 信息过长时截断显示，但保留查看完整内容的方法。

每个危险操作必须：

- 不能只凭菜单编号执行。
- 不能在非交互环境因默认 `Y` 自动执行。
- 必须验证目标路径在安装目录内。
- 必须拒绝符号链接越界和路径穿越。
- 能创建保护点时先创建保护点。
- 操作后进行健康验证。

## 15. 最终建议结论

近期最值得做的不是继续堆更多入口，而是先完成以下六项：

1. 合并迁移预检与迁移计划。
2. 拆分访问地址与敏感密钥。
3. 重排连续、清晰的一级菜单编号。
4. 实现配置体检和快照恢复演练。
5. 实现两套审计的无损清除与历史查看。
6. 实现脱敏诊断包。

明确不应合并的功能：

- 消费行为审计与管理行为审计。
- 创建快照、查看快照与恢复快照。
- 正式迁移与回滚迁移。
- 启动、停止与重启。
- 查看密钥与重新生成密钥。

明确应该删除或退役的内容：

- 旧“安全巡检 / 24h IP”混合入口。
- 旧 `backup` 功能和新数据继续写入 `backups/` 的做法。
- 独立重复的“查看迁移计划”菜单。
- 没有路径依据却强行分类的审计记录。
- 默认自动封禁 IP 的方案。

这样可以在保持一级菜单直达的前提下，让功能边界、安全确认、目录结构和后续开发顺序都更加清晰。
