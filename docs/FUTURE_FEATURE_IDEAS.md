# CLIProxyAPI 与 CPA Manager Plus 后续功能构思

## 1. 文档目的

本文从产品和运维视角整理本仓库在完成当前主线后可以继续开发的能力，供后续评审、拆分版本和安排优先级使用。

涉及的三个边界如下：

- **CLIProxyAPI**：模型代理、认证、路由、请求日志和远程管理接口。
- **CPA Manager Plus**：可视化管理、用量统计和管理操作。
- **本仓库脚本**：安装、升级、迁移、运维编排和安全保护，不复制两个上游项目的完整业务实现。

本文不把下列已有或正在当前主线设计、实现的能力重复列为新功能：一键部署、统一迁移评估、容器状态页、统一状态采集、版本对比升级、基础配置体检、密钥重置、消费与管理两类行为审计、无损清除审计显示基线、统一快照元数据、快照创建/列表/恢复/指定删除、定时快照和自动快照滚动保留。

## 2. 实现边界和优先级

### 2.1 实现边界

| 标记 | 含义 | 典型实现方式 |
| --- | --- | --- |
| `脚本可实现` | 不修改上游源码即可完成 | Bash、Docker、Compose、日志解析、稳定 API、systemd |
| `脚本优先，上游增强` | 可以先实现基础版，上游提供接口后体验更完整 | 脚本采集与编排，上游补充结构化接口或事件 |
| `需要上游配合` | 仅靠外部脚本无法可靠实现 | 修改 CLIProxyAPI 或 CPA Manager Plus 的接口、数据模型或前端 |

### 2.2 优先级

| 优先级 | 含义 | 建议时机 |
| --- | --- | --- |
| P0 | 直接降低配置错误、升级失败、凭证失效或数据丢失风险 | 下一至两个版本 |
| P1 | 明显提升日常运维、安全和成本管理效率 | 核心可靠性完成后 |
| P2 | 面向多实例、团队协作和规模化部署 | 基础功能稳定后 |
| P3 | 高级平台化、生态和实验能力 | 有明确用户需求时 |

## 3. 配置治理与变更安全

### 3.1 配置体检增强与脱敏差异（P0，脚本可实现）

- **用户价值**：在重启或升级前发现 YAML 错误、端口冲突、目录权限、无效镜像和缺失必填项，减少“改完配置服务起不来”。
- **方案轮廓**：基础只读 `doctor` 已实现 Compose、关键配置、端口、权限、SQLite、挂载和磁盘检查；后续增加严格 YAML schema、版本化规则和应用变更前的脱敏差异。
- **风险与依赖**：不同 CLIProxyAPI 版本的配置字段可能变化，需要维护版本化规则；密钥只能显示摘要，不能出现在差异正文。

### 3.2 配置版本库与一键回退（P0，脚本可实现）

- **用户价值**：知道配置何时、因为什么被修改，并能只回退配置而不恢复全部业务数据。
- **方案轮廓**：每次脚本修改前保存规范化配置、变更原因、操作者、镜像摘要和校验值；提供配置历史列表、差异查看和指定版本恢复。
- **风险与依赖**：历史目录必须为 `0700`，文件为 `0600`；不能把完整密钥提交到 Git 或普通日志。

### 3.3 部署策略模板（P1，脚本可实现）

- **用户价值**：新手无需理解全部参数，也能选择“个人低配”“生产稳定”“内网受限”等安全默认值。
- **方案轮廓**：提供少量经过验证的配置档案，安装确认页明确列出端口暴露、日志级别、版本通道、资源限制和保留策略。
- **风险与依赖**：模板不能无限增多；用户自定义值必须有清晰优先级，升级时不能静默覆盖。

### 3.4 配置漂移检测（P1，脚本可实现）

- **用户价值**：发现有人绕过脚本手工改了 Compose、配置或容器参数，避免下次升级意外覆盖。
- **方案轮廓**：记录最后一次受管状态的校验值，巡检时与磁盘文件及运行容器配置对比，显示“文件变化”“运行态变化”“镜像变化”。
- **风险与依赖**：只报告和生成修复建议，不应默认覆盖人工修改；需要排除时间戳等非语义差异。

## 4. 版本发布与升级治理

### 4.1 稳定、候选和固定版本通道（P0，脚本可实现）

- **用户价值**：生产环境可以锁定已验证版本，测试环境可以提前体验新版本，不再被 `latest` 的内容变化被动升级。
- **方案轮廓**：支持固定 tag、固定 digest、候选通道和浮动最新通道；状态页同时显示版本、镜像摘要和发布时间。
- **风险与依赖**：上游镜像标签和版本元数据可能不规范；无法识别语义版本时必须降级为摘要比较。

### 4.2 发布说明聚合与风险提示（P1，脚本优先，上游增强）

- **用户价值**：升级前直接看到破坏性变更、配置迁移、数据库变化和已知问题。
- **方案轮廓**：从 GitHub Release 或维护的兼容矩阵读取当前版本到目标版本之间的说明，按“安全”“配置”“数据”“接口”分类展示。
- **风险与依赖**：需要网络和可靠的版本映射；自动摘要不能替代原始发布说明，信息不足时应明确提示人工确认。

### 4.3 分阶段升级与观察窗口（P1，脚本可实现）

- **用户价值**：升级后先观察健康、错误率和容器重启次数，再决定接受新版本或回退。
- **方案轮廓**：升级完成后进入可配置观察期，连续检查健康端点、鉴权、日志错误和容器状态；达到失败阈值时给出自动回退选项。
- **风险与依赖**：真实模型探测可能产生费用；默认只做无费用检查，付费探测必须单独确认。

### 4.4 蓝绿或旁路验证（P2，脚本优先，上游增强）

- **用户价值**：在不替换生产容器前，用临时端口验证新版本读取配置和数据的兼容性。
- **方案轮廓**：创建隔离的临时 Compose 项目、只读复制数据和独立网络，验证成功后再切换生产容器。
- **风险与依赖**：不能让两个 Manager 同时消费同一队列；涉及 SQLite 和认证文件时必须隔离，无法保证只读的版本应禁止旁路启动。

## 5. 凭证与认证生命周期

### 5.1 凭证健康度清单（P0，脚本可实现）

- **用户价值**：快速知道认证文件数量、最后更新时间、权限异常、空文件、重复文件和即将失效的凭证。
- **方案轮廓**：只读取元数据和可安全解析的过期字段，按健康、警告、失效、未知分类，不输出令牌正文。
- **风险与依赖**：不同供应商凭证格式不统一；未知格式只能报告文件级状态，不能猜测有效性。

### 5.2 凭证到期提醒（P1，脚本优先，上游增强）

- **用户价值**：在 OAuth 或账户凭证失效前收到提醒，避免模型调用突然中断。
- **方案轮廓**：定期检查显式过期时间、最近刷新失败和连续鉴权错误；支持本地提示、Webhook 或邮件通知。
- **风险与依赖**：部分凭证没有可读取的到期时间；通知中不得携带文件内容、邮箱全称或完整账户标识。

### 5.3 凭证隔离、标签和使用范围（P1，需要上游配合）

- **用户价值**：给凭证标注团队、环境、供应商和允许模型，降低凭证被错误路由或跨环境使用的风险。
- **方案轮廓**：CLIProxyAPI 提供凭证元数据、标签和策略接口；Manager 提供筛选、批量维护和冲突提示。
- **风险与依赖**：需要上游建立稳定凭证 ID，不能用文件名作为长期身份；标签变更需进入管理行为审计。

### 5.4 无损凭证轮换窗口（P2，需要上游配合）

- **用户价值**：新旧凭证可短期并存，确认新凭证工作后再撤销旧凭证，降低轮换中断。
- **方案轮廓**：上游支持凭证启用状态、优先级、试运行和排空；脚本负责轮换编排与最终确认。
- **风险与依赖**：双凭证窗口会扩大泄露面，必须有短时限、明确撤销动作和失败回滚。

## 6. 模型路由与服务质量

### 6.1 模型目录与可用性矩阵（P1，脚本优先，上游增强）

- **用户价值**：集中查看每个供应商提供哪些模型、当前是否可用、最近失败原因和能力差异。
- **方案轮廓**：合并 `/v1/models`、配置和轻量探测结果，按模型展示文本、视觉、工具调用、上下文等能力标签。
- **风险与依赖**：能力标签不能仅靠模型名称猜测；上游提供结构化元数据后才能保证准确。

### 6.2 路由规则模拟器（P1，需要上游配合）

- **用户价值**：修改路由前输入模型、用户、来源和请求特征，预览会命中哪个凭证、上游和回退规则。
- **方案轮廓**：CLIProxyAPI 暴露不产生真实调用的 `dry-run` 路由接口，Manager 提供可视化解释链。
- **风险与依赖**：模拟器必须复用真实路由代码，否则结果会漂移；输出不能暴露完整凭证信息。

### 6.3 熔断、降级与自动恢复策略（P1，需要上游配合）

- **用户价值**：某供应商限流或故障时自动转移到备用模型，并在恢复后逐步切回。
- **方案轮廓**：按连续错误、状态码、延迟设置熔断阈值，支持半开探测、优先级回退和最大降级次数。
- **风险与依赖**：替代模型可能价格、能力和数据区域不同；必须允许禁止跨供应商或跨模型族降级。

### 6.4 延迟与成功率驱动的动态路由（P2，需要上游配合）

- **用户价值**：在多个可用上游之间自动选择更稳定或更快的线路。
- **方案轮廓**：使用滑动窗口统计延迟、限流和失败率，按权重调整流量，并保留最小探测流量。
- **风险与依赖**：小样本容易抖动，需要冷却时间和人工锁定；不能只追求延迟而忽略成本和模型质量。

### 6.5 请求级追踪编号（P1，需要上游配合）

- **用户价值**：用户报错时凭一个编号串起代理日志、路由决策、上游响应和 Manager 统计。
- **方案轮廓**：入口生成或透传 trace ID，结构化日志记录各阶段耗时，Manager 支持按编号查询脱敏链路。
- **风险与依赖**：编号不能编码用户或密钥信息；需要控制保留周期和查询权限。

## 7. 用量、成本与配额治理

### 7.1 预算阈值与分级提醒（P1，需要上游配合）

- **用户价值**：按日、周、月控制总预算，提前发现费用异常，而不是月底才看到结果。
- **方案轮廓**：Manager 维护预算和阈值，按全局、模型、凭证或标签统计；达到 50%、80%、100% 时采用不同提醒级别。
- **风险与依赖**：不同供应商计价和缓存规则不同；没有准确价格表时只能标记为估算，不能执行强制停用。

### 7.2 团队、项目和 API Key 配额（P1，需要上游配合）

- **用户价值**：避免单个项目耗尽所有额度，支持团队内部成本归属和公平使用。
- **方案轮廓**：为调用 Key 增加项目标签、速率、并发、Token 和金额配额，Manager 展示剩余额度与超限原因。
- **风险与依赖**：需要 CLIProxyAPI 在请求入口强制执行；配额状态要考虑并发一致性和重启恢复。

### 7.3 成本异常检测（P1，脚本优先，上游增强）

- **用户价值**：自动发现某模型、Key 或时间段消费突然放大，及时止损。
- **方案轮廓**：先用历史中位数、同比时段和倍率阈值生成异常提示；上游提供结构化用量后再扩展更细粒度检测。
- **风险与依赖**：新业务增长可能造成误报；默认只告警，不自动停用调用方。

### 7.4 价格表版本化与账单估算（P2，需要上游配合）

- **用户价值**：历史费用按照调用发生时的价格计算，避免模型调价后重算结果失真。
- **方案轮廓**：维护带生效时间的价格表，记录输入、输出、缓存和特殊 Token 计价版本，并支持人工覆盖。
- **风险与依赖**：价格来源、币种、税费和阶梯价复杂；界面必须区分“官方账单”和“本地估算”。

### 7.5 容量预测与额度耗尽时间（P2，需要上游配合）

- **用户价值**：根据近几日趋势预测当前额度还能使用多久，便于提前补充凭证或调整路由。
- **方案轮廓**：提供 7/30 天趋势和简单置信区间，按总量、供应商和项目估算耗尽时间。
- **风险与依赖**：数据不足或波动过大时应显示“无法可靠预测”，不能输出虚假精确时间。

## 8. 可观测性、诊断与告警

### 8.1 服务质量摘要（P1，脚本可实现）

- **用户价值**：一次查看最近 1 小时、24 小时、7 天的成功率、状态码、延迟分位数和高频模型。
- **方案轮廓**：流式解析日志，输出总览卡片和异常项；格式无法识别时显示诊断计数，不把缺失数据当作零。
- **风险与依赖**：旧日志格式变化会影响准确性，需要保留官方格式样例和回归测试。

### 8.2 统一告警适配器（P1，脚本可实现）

- **用户价值**：备份失败、磁盘不足、健康异常、凭证失效和调用错误激增可统一通知。
- **方案轮廓**：定义本地事件格式和去重冷却机制，再接入通用 Webhook、邮件或自定义命令；默认仅生成配置，不自动启用。
- **风险与依赖**：必须防止告警风暴；消息只包含摘要和本地排查命令，不包含密钥或请求正文。

### 8.3 脱敏诊断包（P0，脚本可实现）

- **用户价值**：遇到问题时能安全地向维护者提供版本、状态、配置结构和错误上下文。
- **方案轮廓**：收集镜像摘要、容器状态、健康结果、脱敏配置和有限错误日志；生成前后各执行一次敏感信息扫描。
- **风险与依赖**：IP、账户、路径也可能属于敏感数据；打包前必须展示收集清单，上传动作始终由用户完成。

### 8.4 Prometheus 指标与结构化日志（P2，需要上游配合）

- **用户价值**：可以接入现有 Grafana、Loki 或企业监控体系，而不依赖终端临时统计。
- **方案轮廓**：上游提供请求量、延迟、Token、路由、凭证状态等低基数指标，并输出稳定 JSON 日志。
- **风险与依赖**：模型名、用户 ID 等高基数标签会造成指标系统膨胀；敏感字段必须默认关闭。

### 8.5 一键生成排障时间线（P2，脚本优先，上游增强）

- **用户价值**：自动把升级、重启、配置变化、健康失败和调用异常按时间对齐，帮助定位“从什么时候开始坏”。
- **方案轮廓**：合并脚本操作日志、Docker 事件、审计事件和健康结果，输出脱敏 Markdown 时间线。
- **风险与依赖**：各数据源时区和时间精度不同；必须标明数据缺口，不能把时间接近当作因果关系。

## 9. 安全与合规

### 9.1 最小暴露面向导（P0，脚本可实现）

- **用户价值**：安装后立即发现管理端口直接暴露公网、弱文件权限或未启用 HTTPS 等问题。
- **方案轮廓**：检查监听地址、端口映射、UFW、反向代理、密钥权限和 Docker Socket；生成逐项修复建议。
- **风险与依赖**：脚本不能擅自修改云安全组；防火墙变更可能锁死 SSH，必须明确确认并保留回退命令。

### 9.2 反向代理与 TLS 配置向导（P1，脚本可实现）

- **用户价值**：减少明文传输管理密钥和 API Key 的风险，统一域名和证书续期检查。
- **方案轮廓**：生成 Caddy 或 Nginx 模板，支持管理面板与 API 分域名、访问控制和安全响应头。
- **风险与依赖**：域名、DNS 和证书签发依赖外部环境；不能在未确认 80/443 端口和现有站点时覆盖配置。

### 9.3 安全基线评分（P1，脚本可实现）

- **用户价值**：用可解释的检查项快速判断部署风险，并看到整改优先级。
- **方案轮廓**：围绕公网暴露、TLS、版本固定、文件权限、备份可恢复性、日志保留和失败调用设置规则，不采用黑盒“安全分”。
- **风险与依赖**：评分只是配置基线，不等同于漏洞扫描或入侵结论；每项扣分必须给出证据。

### 9.4 IP 风险策略建议（P1，脚本可实现）

- **用户价值**：把高频失败、敏感路径探测、代理/机房标记转成可审查的防护建议。
- **方案轮廓**：生成 UFW、nftables 或反向代理规则草案，包含命中证据、过期时间和撤销命令。
- **风险与依赖**：共享出口、企业 NAT 和内网代理容易误伤；默认永不自动封禁，第三方 IP 查询需用户确认。

### 9.5 数据保留与隐私模式（P2，需要上游配合）

- **用户价值**：按组织要求控制请求日志、IP、模型调用明细和审计记录的保留时长及脱敏级别。
- **方案轮廓**：上游支持字段级日志开关、IP 哈希或截断、保留策略和受控导出；Manager 展示策略生效范围。
- **风险与依赖**：删除策略可能影响故障取证和统计连续性；必须区分业务统计、审计和原始日志。

### 9.6 软件供应链验证（P1，脚本优先，上游增强）

- **用户价值**：确认部署的是预期镜像内容，并能追溯每次运行的不可变版本。
- **方案轮廓**：至少记录镜像 digest；条件允许时校验签名、来源和 SBOM，发现同 tag 摘要变化时明确告警。
- **风险与依赖**：需要上游发布签名或可信摘要；未签名不应被错误描述为恶意，只能标记“无法验证”。

## 10. 自动化、灾备与资源治理

### 10.1 计划任务中心（P1，脚本可实现）

- **用户价值**：统一管理定时快照、健康巡检、版本检查、凭证到期检查和报告生成。
- **方案轮廓**：生成 systemd service/timer，列表展示任务、下次执行、最近结果和日志入口；默认生成但不启用。
- **风险与依赖**：多个任务不能同时执行高风险操作，需要文件锁、超时和错峰策略。

### 10.2 异地副本与加密导出（P1，脚本可实现）

- **用户价值**：服务器磁盘损坏或误删时，仍有可恢复的站外副本。
- **方案轮廓**：在本地快照验证通过后，可选使用 `age` 加密并复制到用户配置的 S3 兼容存储、SSH 目标或挂载盘。
- **风险与依赖**：远端凭证管理、带宽和存储费用由用户承担；加密私钥丢失将无法恢复，上传失败不能影响本地副本。

### 10.3 自动恢复演练（P0，脚本可实现）

- **用户价值**：证明快照不只是“能解压”，而是真的具备恢复价值。
- **方案轮廓**：在临时目录验证清单、校验值、关键文件、SQLite 完整性和镜像可用性；可选启动隔离容器做只读健康检查。
- **风险与依赖**：隔离演练不能连接生产队列或占用生产端口；磁盘空间不足时只执行静态校验。

### 10.4 磁盘容量预测与清理建议（P1，脚本可实现）

- **用户价值**：提前知道日志、快照和数据库何时可能占满磁盘。
- **方案轮廓**：统计目录增长速度、剩余空间和预计耗尽时间，生成按收益排序的清理建议；快照删除仍需逐个确认。
- **风险与依赖**：增长趋势波动时只能给区间；不得自动删除上游数据、当前快照或未知文件。

### 10.5 容器资源限制和异常检测（P1，脚本可实现）

- **用户价值**：避免日志暴涨、异常请求或数据库问题拖垮整台服务器。
- **方案轮廓**：安装向导可配置 CPU、内存、日志轮转和重启策略；巡检显示 OOM、重启次数和资源持续偏高。
- **风险与依赖**：默认限制过低会影响长请求；应先观察再建议，不对已有部署静默加限制。

### 10.6 故障演练模式（P2，脚本可实现）

- **用户价值**：提前验证容器退出、端口占用、磁盘逼近阈值等情况下告警和恢复流程是否有效。
- **方案轮廓**：仅在隔离测试实例注入有限故障，记录预期、实际结果和恢复步骤。
- **风险与依赖**：生产实例默认禁止；必须设置最大持续时间和自动清理，不能模拟数据破坏。

## 11. 多实例、团队和平台化

### 11.1 多实例档案（P2，脚本可实现）

- **用户价值**：一台服务器安全管理生产、测试或不同客户实例，避免端口、目录和密钥串用。
- **方案轮廓**：每个实例拥有独立名称、Compose 项目、目录、端口、快照库和状态文件；所有命令首行显示当前实例。
- **风险与依赖**：实例之间禁止共享 Manager 数据和凭证目录；删除实例要分别确认服务、数据和快照。

### 11.2 远程主机清单与批量只读巡检（P2，脚本可实现）

- **用户价值**：从运维机查看多台服务器的版本、健康、磁盘和待处理事项。
- **方案轮廓**：通过 SSH 执行只读状态命令，输出汇总表；写操作仍逐台确认，不提供默认批量升级。
- **风险与依赖**：需要安全的 SSH 配置和主机指纹校验；不能集中保存上游业务密钥。

### 11.3 角色权限和双人确认（P2，需要上游配合）

- **用户价值**：区分只读观察、凭证管理、升级运维和超级管理员，降低单个密钥权限过大。
- **方案轮廓**：Manager 建立角色权限；高风险操作可生成待审批记录，由第二位管理员确认后执行。
- **风险与依赖**：需要可靠的用户身份、会话和审计模型；单机个人部署应保持简单模式。

### 11.4 运维 API 与自动化输出（P2，脚本可实现）

- **用户价值**：让 Ansible、监控系统或自建面板安全调用状态、巡检和快照等能力。
- **方案轮廓**：先提供稳定的 `--json` 输出和明确退出码，再考虑本地 Unix Socket 服务；危险动作要求一次性确认令牌。
- **风险与依赖**：不能把交互文本当作 API；需要版本化输出结构和向后兼容策略。

## 12. 数据能力与用户体验

### 12.1 报告导出中心（P1，脚本优先，上游增强）

- **用户价值**：按时间、模型、项目和状态导出 CSV/JSON/Markdown，用于复盘和内部报表。
- **方案轮廓**：脚本先提供运维报告导出；Manager 再提供结构化用量与审计导出接口，支持字段选择和脱敏预览。
- **风险与依赖**：大范围导出需流式处理；导出文件可能包含 IP 或业务标识，默认权限必须严格。

### 12.2 自定义仪表盘与保存视图（P2，需要上游配合）

- **用户价值**：不同角色可以保存关注的时间范围、模型、项目和异常指标，不必每次重新筛选。
- **方案轮廓**：Manager 支持组件化卡片、筛选条件和只读分享视图。
- **风险与依赖**：避免演变成复杂 BI 平台；首版只支持少量固定组件和本地保存。

### 12.3 中文错误解释与修复向导（P1，脚本可实现）

- **用户价值**：把容器错误、401、403、429、端口冲突和数据库锁等信息翻译成可执行步骤。
- **方案轮廓**：维护证据驱动的错误规则库，每条包含现象、可能原因、确认命令、低风险修复和回退方式。
- **风险与依赖**：不能只凭关键词自动执行修复；不确定时保留原始错误并提示人工判断。

### 12.4 首次部署验收清单（P0，脚本可实现）

- **用户价值**：安装完成不只显示“容器已启动”，而是确认访问、鉴权、持久化、权限和恢复条件都符合预期。
- **方案轮廓**：安装后生成验收报告，包含健康端点、端口、目录权限、关键文件、镜像摘要、初始快照和下一步安全建议。
- **风险与依赖**：不能把真实密钥写进普通报告；外网连通性需要区分本机检查与用户侧检查。

### 12.5 可复现的问题报告（P1，脚本可实现）

- **用户价值**：提交 Issue 时自动带上必要环境信息和复现步骤，减少来回追问。
- **方案轮廓**：根据最近失败操作生成 Markdown 模板，引用脱敏诊断包摘要、预期结果、实际结果和已尝试步骤。
- **风险与依赖**：只生成本地文件，不自动上传；必须提醒用户人工复核敏感内容。

## 13. 上游协同与生态扩展

### 13.1 上游能力探测与兼容层（P0，脚本可实现）

- **用户价值**：同一脚本能安全适配不同版本，而不是假定所有接口和命令都存在。
- **方案轮廓**：启动时探测版本、端点和命令能力，形成能力集合；功能按能力启用，缺失时说明最低版本和替代路径。
- **风险与依赖**：探测必须只读且有超时；不能把一次网络失败误判为永久不支持。

### 13.2 结构化事件接口（P1，需要上游配合）

- **用户价值**：行为审计、告警和统计无需依赖易变化的文本日志正则。
- **方案轮廓**：CLIProxyAPI 输出稳定事件 schema，区分消费、管理、系统探测和路由阶段；包含脱敏主体、结果和 trace ID。
- **风险与依赖**：需要 schema 版本和兼容策略；事件中不得包含请求正文、Authorization 或完整凭证。

### 13.3 稳定管理 API 与 OpenAPI 文档（P1，需要上游配合）

- **用户价值**：脚本和第三方工具可以可靠完成配置查询、凭证状态、用量导出和健康诊断。
- **方案轮廓**：上游为受支持接口提供版本化 OpenAPI、错误码、权限范围和弃用周期。
- **风险与依赖**：接口暴露会扩大攻击面，必须采用最小权限、速率限制和安全默认监听地址。

### 13.4 插件式通知和存储适配器（P3，脚本优先，上游增强）

- **用户价值**：用户可以扩展通知渠道、异地存储和报告出口，而无需修改主脚本。
- **方案轮廓**：定义窄接口的可执行适配器，输入经过脱敏的 JSON，输出明确退出码；维护官方示例而非内置所有平台。
- **风险与依赖**：第三方插件等同于本机代码执行，必须由用户安装、固定路径并明确标注信任边界。

## 14. 推荐实施组合

### 14.1 近期版本：可靠性闭环

1. 配置体检与脱敏差异。
2. 配置版本库与一键回退。
3. 脱敏诊断包。
4. 自动恢复演练。
5. 首次部署验收清单。
6. 上游能力探测与兼容层。

**完成标准**：安装、配置变更和恢复都有可读报告；失败能定位，敏感信息不泄露，无法支持的上游能力不会被误调用。

### 14.2 中期版本：主动运维

1. 凭证健康度与到期提醒。
2. 服务质量摘要与统一告警。
3. 计划任务中心。
4. 磁盘容量预测。
5. 最小暴露面向导与 TLS 配置向导。
6. 发布说明聚合和升级观察窗口。

**完成标准**：常见风险可以在故障发生前被发现，告警可去重、可追踪，并且每条告警都有本地证据和处理建议。

### 14.3 后期版本：治理与规模化

1. 团队和项目配额。
2. 路由模拟、熔断和动态路由。
3. 多实例与多主机巡检。
4. 角色权限和双人确认。
5. Prometheus、结构化日志和稳定管理 API。
6. 数据保留、隐私模式和报告导出中心。

**完成标准**：多个实例、团队和自动化系统能在权限、成本、审计和数据隔离边界内协同运行。

## 15. 暂不建议开发的方向

- **默认自动封禁 IP**：容易误伤共享出口和合法代理，只生成带撤销方式的建议。
- **自动上传完整日志或诊断包**：可能泄露密钥、IP 和请求内容，始终由用户人工复核和上传。
- **在 Bash 中重写完整管理后台**：会与 CPA Manager Plus 重复并扩大维护面，界面能力优先向上游贡献。
- **无版本门禁的数据库直接修改**：上游结构变化后容易损坏数据，优先使用公开 API 或受支持命令。
- **默认开启批量自动升级**：多实例同时失败会放大影响，应先只读检查、分批确认和设置观察窗口。
- **仅凭 IP 归属判定攻击**：归属、代理和机房标签只能作为线索，必须结合行为、频率和认证结果。
- **把本地估算当成供应商账单**：模型价格和计费规则可能变化，所有成本推算必须明确标注来源与误差。

## 16. 统一产品与验收原则

- 一级菜单直接展示主要功能，不把常用操作藏进多级目录。
- 状态、列表和确认页使用统一列宽、分区、成功/警告/失败图标，避免信息堆叠。
- 所有写操作先显示目标实例、对象、路径、当前状态、影响范围和回退方式。
- 高风险操作不能因全局默认确认而跳过二次核对；非交互模式必须显式授权。
- 不在终端历史、普通日志、报告和通知中输出完整密钥、Token、Authorization 或凭证正文。
- 外部 API 调用前说明发送内容、传输方式、隐私风险和失败降级策略。
- 上游接口或日志信息不足时显示“未知”或“无法判断”，不伪造成功、零值或精确结论。
- 每个新增功能都应提供模拟测试、失败测试、文档和稳定的非交互退出码。
- 所有状态文件采用原子写入、严格权限和损坏回退，不修改上游原始日志与业务数据库来实现界面效果。
- 优先做可回退、可验证的小闭环，再推进需要两个上游协同的大型平台能力。
